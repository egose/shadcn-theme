# Angular shadcn-theme standard example

Consumer example for `@egose/shadcn-theme-ng`: a catalog of isolated
component demos plus realistic product flows (pricing, team management,
settings, support inbox) composed only from the package's public exports.
It uses Angular 22 standalone components, zoneless change detection, strict
templates, and production bundle budgets.

## Install

This example lives in the nested pnpm workspace rooted at
`packages/angular` (see `pnpm-workspace.yaml`, which includes
`@examples/*`). Install once from there:

```bash
pnpm --dir packages/angular install
```

That links every dependency the example declares in its own
`package.json` into `packages/angular/@examples/standard/node_modules`.
The example manifest declares all of its direct imports (Angular,
`@spartan-ng/brain`, icons, Sonner, `rxjs`, …); `@angular/cdk` is
intentionally absent because no example source imports it directly.

Headless-test prerequisite (local and CI): the Karma suite needs a
Chrome-compatible binary. The repository-supported setup downloads it into
the repo-local `.puppeteer-cache/` directory:

```bash
pnpm --dir packages/angular/@examples/standard install:browser
```

Alternatively, set `CHROME_BIN` to any Chrome/Chromium binary yourself
(`karma.conf.js` honors a pre-set `CHROME_BIN`).

## Start, build, test

All commands run in `packages/angular/@examples/standard`
(`pnpm --dir packages/angular/@examples/standard <script>` from the repo
root, or `pnpm <script>` inside the directory):

```bash
pnpm start        # ng serve — local dev server on http://localhost:4200/
pnpm build        # ng build — production AOT build with strict templates
pnpm test         # ng test — Karma in watch mode (needs the browser setup above)
pnpm test:ci      # node scripts/test-ci.mjs — headless run, fails on zero specs
```

`test:ci` spawns `ng test --watch=false`, propagates its exit code, and
parses the Karma `Executed N of M` summary so a broken spec glob or an
empty suite can never look like a green run.

## Quality commands

```bash
pnpm sync:aliases   # regenerate tsconfig path aliases + subpath imports from publishable-projects.json
pnpm smoke:deploy   # serve dist/angular/browser with Pages semantics and assert registry-derived routes over HTTP
```

`smoke:deploy` requires a production `build` first (plus the fallback
copies the deploy workflow creates — see Deployment below). Run it from the
example directory.

Package-level checks relevant to this example (run in `packages/angular`):

```bash
pnpm test:example-boundary  # alias freshness, import boundary, manifest completeness, prefix semantics
pnpm test:variants           # plain vs -tw build behavior
pnpm verify:consumers --release-dir release  # exact-tarball consumer builds (after prepare:release)
```

Pull-request CI (`.github/workflows/test.yml`, `angular` job) runs, in
order: the package source tests including `test:example-boundary`, then
`install:browser`, then the example `build` and `test:ci`, and only then
the release/consumer packaging — example gates complete before release
checks.

## Source integration vs exact-tarball validation

Local development consumes package **source** through TypeScript path
aliases: every `@egose/shadcn-theme-ng/*` subpath maps to
`../../projects/*/src/public-api.ts`. The alias block in `tsconfig.json`
and `src/app/example-subpaths.generated.ts` are generated by
`pnpm sync:aliases` from `packages/angular/publishable-projects.json`
(the package source of truth), so no subpath can go stale — but this is
fast source integration only. **It does not validate `dist` output or npm
exports.**

Published-artifact claims come only from exact-tarball checks in
`packages/angular`: `prepare:release` builds plain and `-tw` tarballs and
`verify:consumers` installs them into fresh isolated consumers that run a
strict install, typecheck, production build, stylesheet prefix-identity
assertion, and SSR render class-identity assertion. An import-boundary test
(`consumer-boundary.spec.ts` locally, `test:example-boundary` at package
level) rejects private `/src/lib` deep imports, `dist` imports, parent
`node_modules` reach-through, `-tw` imports in source mode, and
unregistered subpaths.

## Plain vs `-tw` prefix semantics

This example's `src/styles.css` imports Tailwind with `prefix(tw)` and
scans package **source** (`@source "../../../projects"`), so local
development exercises real `tw:` utilities. The two published variants
differ exactly in class prefixing:

- **plain**: unprefixed utilities (built CSS contains `.inline-flex`,
  never `tw:`);
- **`-tw`**: `tw:`-prefixed utilities (built CSS contains
  `tw\:inline-flex`, never an unprefixed leak).

Consumers of `-tw` set the same `prefix(tw)` config and point `@source` at
the installed tarball. The prefix identity of both variants is asserted by
the isolated-consumer builds (`verify:consumers`), not by this example's
source-mode build.

## Typed registry and directory conventions

`src/app/catalog/catalog.ts` is the single source of truth. One
`CatalogEntry` — `{ slug, title, category, kind, load }` — creates the lazy
child route, the menu item, the search option, and any displayed count:

- `kind: 'component'` → isolated primitive demo under
  `/components/<slug>`, implemented at
  `src/app/pages/components/<slug>/<slug>.ts`.
- `kind: 'example'` → realistic product flow under `/examples/<slug>`,
  implemented as a feature directory at
  `src/app/pages/examples/<slug>/` (route component, local components,
  typed models, deterministic fixtures, colocated specs).

Child routes (`catalogChildRoutes`), menu groups (`catalogMenuGroups`),
search options, and counts are all derived from the registry; contract
tests (`catalog.spec.ts`, `app.routes.spec.ts`) fail on duplicate
slugs/titles/links, missing loaders, or removals below the reviewed
baselines (`REVIEWED_COMPONENT_BASELINE`, `REVIEWED_EXAMPLE_BASELINE`).
Real examples never appear in component menus and vice versa. Unknown URLs
render an intentional accessible not-found page (`pages/not-found/`).

### Adding a component demo

1. Create `src/app/pages/components/<slug>/<slug>.ts` as a standalone
   component: render the routed title with `app-demo-header` (exactly one
   `h2`, no `h1`), sections with `app-demo-section`/`app-demo-matrix` or
   plain `h3` markup, and keep package component markup visible at the call
   site (framing components only project content).
2. Add one registry entry
   `{ slug: '<slug>', title: '<Title>', category: '<Group>', kind: 'component', load: () => import('../pages/components/<slug>/<slug>').then((m) => m.<Name>Page) }`.
3. Run `pnpm build` and `pnpm test:ci` — routing, menu, search, count,
   heading-hierarchy, and responsive suites pick the entry up with no other
   edits.

### Adding a real example

1. Create `src/app/pages/examples/<slug>/` with the route component,
   colocated typed models, deterministic fixtures (`<slug>-fixtures.ts`),
   and a colocated `<slug>.spec.ts`. Reuse the shared state tooling
   (`src/app/shared/real-examples/`: `example-state-toolbar`,
   `async-simulator`, `example-view-state`) for loading/empty/error/loaded
   and read-only previews.
2. Add one registry entry with `kind: 'example'`.
3. Run `pnpm build`, `pnpm test:ci`, and `pnpm smoke:deploy` — the
   `/examples` routes, Examples catalog surface, and deployment smoke
   checks derive from the same entry.

## Fixtures, interaction, and accessibility expectations

- Fixtures are deterministic: fixed UTC ISO date strings (always ending in
  `Z`), stable IDs, varied text lengths, and local initials/image
  fallbacks. No live APIs, auth providers, payment services, remote image
  hosts, current-time defaults, or random outcomes. Explicit simulated
  outcomes only.
- Every demonstrated form control has a visible label or an intentional
  accessible-name mechanism; icon-only controls have explicit names with
  pressed/expanded state where applicable.
- Navigation examples use real local routes or explicit external `https://`
  URLs — never `href="#"`, and action-only anchors are buttons.
- **No-op primary actions are forbidden.** Every visible primary action
  must change visible state, navigate, or be explicitly marked as
  disabled/demo-only. Outcomes are visible (`role="status"`/`role="alert"`,
  toasts, committed values) — never console-only.
- Heading contract: gallery `h1` → routed page title `h2` (via
  `app-demo-header`) → sections `h3` → component-internal headings at
  descendant levels. Pages must fit 320px viewports without horizontal page
  overflow (except components intentionally demonstrating horizontal
  scrolling).
- Shared UI/state helpers require at least two consumers; otherwise keep
  them colocated with the owning example. Domain blocks stay local until
  repeated use proves a shared abstraction.

Non-visual `utils` (`hlm()` clsx + tailwind-merge contract) has no gallery
page by design; it is covered by the focused `src/app/utils-usage.spec.ts`
instead.

## Deployment and deep links

Strategy: **registry-derived prerendering with shell-copy fallbacks.**
`angular.json` sets production `prerender: true`; the prerendered route set
is discovered from the Router config, which is derived from the typed
registry — there is no second slug list. The app is served from the root of
the `pages-angular` branch (`base href` stays `/`).

`.github/workflows/deploy-angular.yml` builds, then materializes the Pages
fallback contract from the CSR shell before deploying:

- `index.csr.html` → `index.html`, `404.html`, `components/index.html`,
  `examples/index.html` (covering the `/`, `/components`, and `/examples`
  redirect roots plus unknown URLs), plus `.nojekyll`;
- then runs `pnpm smoke:deploy`, which serves `dist/angular/browser` with
  Pages semantics and asserts over HTTP: root boots, every registry route
  loads its prerendered `>Title</h2>`, unknown URLs fall back to the shell
  (the client router renders the not-found page), and every prerendered
  route directory maps back to a registry entry.
